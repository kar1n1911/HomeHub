## 1｜00:00–00:40｜应用与三页面导航

[打开 Overview，依次点击 Tasks、Devices，再回 Overview。]

大家好，这是我的微服务项目 HomeHub。它帮助家庭成员管理共享任务、登记设备，并查看设备信号的传输状态。

界面分为三个页面。Overview 提供家庭状态和待办汇总；Tasks 用来创建和完成任务；Devices 用来管理设备和查看信号。点击导航时，页面内容和选中状态一起变化，也支持刷新以及浏览器前进、后退。

接下来，我会演示实际操作，再介绍服务架构、Kubernetes 部署和安全方面的考虑。

## 2｜00:40–01:40｜架构与服务职责

[切到架构图，按讲解顺序指向组件。]

浏览器加载 React 页面，通过 Nginx 访问后端 REST API。家庭服务负责家庭和成员信息，任务服务负责任务及完成状态，设备服务负责设备资料、读数和采样计划。它们分别部署，可以独立增加副本。

业务数据存储在独立运行的 PostgreSQL 集群中。不同服务使用自己的数据库和受限账号，避免所有业务共享同一套数据库凭据。

设备信号还有一条异步处理链路。设备服务先把读数和待发送记录一起保存，collector 再把消息写入持久队列，worker 将 JSON 发送给 HTTP 接收服务，接收服务保存并去重。

这里的 Alertmanager 是项目自定义的信号服务，不是 Prometheus Alertmanager。采集、发送和接收采用不同执行角色，其中发送 worker 可以根据积压独立扩缩容。

## 3｜01:40–02:25｜证明 Kubernetes 正在运行

[终端显示 context、Deployments、Pods、Services、PVC 和数据库集群。]

现在看到的是 OrbStack 的 Kubernetes 集群，应用资源位于 homehub 命名空间。

这里可以看到各应用的 Deployment 和 Pod。前端通过 NodePort 三万零八十端口对外提供访问，所以集群外的浏览器可以打开应用。

数据库由 CloudNativePG 管理，配置了三个实例，每个实例有自己的持久卷。应用 Pod 的生命周期与数据库存储分开，替换应用容器不会要求重新创建业务数据。

本机演示使用单节点配置，因此三个数据库副本仍然共享同一台电脑，这一点会限制故障容忍范围。

## 4｜02:25–03:45｜创建、完成并刷新任务

我先进入 Tasks 页面，创建一条采购清单任务。这个表单会向任务服务发送 POST 请求，由服务校验内容并写入数据库。

[等新任务出现，再勾选完成。]

现在任务已经出现在列表中。勾选完成后，页面发送 PATCH 请求更新它的状态。完成状态得到服务端确认后，界面才显示保存结果。

[点击 Completed，展示新任务；刷新。]

这里可以筛选已完成的任务。现在刷新页面，地址仍然指向 Tasks，新任务也仍然处于完成状态。刷新后筛选回到默认的 All，但任务本身的状态已经保存在服务端。

Overview 的汇总也能反映保存后的任务状态。这说明不同页面围绕同一份业务数据协作。稍后我会结合持久卷和恢复测试，进一步说明容器重启后的数据保留。

## 5｜03:45–05:00｜设备、采样与 JSON 信号

[进入 Devices，Add device，按计划填写 Demo kitchen sensor、Kitchen、22.5 C、30 秒，保存。]

接下来登记一个厨房传感器。这里使用的是模拟设备适配器，并没有连接真实硬件。我设置初始读数和三十秒采样间隔。

保存时，设备信息和第一条待发送信号会一起写入数据库。不同设备的采样时间会错开，多个 collector 通过数据库领取工作，减少重复抓取。不变的读数不会每次都发送，但系统仍会按规则发送心跳。

[指向新设备对应的信号，展开 JSON。]

这条 JSON 包含唯一消息 ID、原始时间、来源和设备数据。后台 worker 将它发送到本地 HTTP 接收服务。

[仅在显示 Delivered 时朗读下一句。]

现在状态是 Delivered，说明接收端已经确认保存。

[如果仍是 Pending，改说：]

现在它仍在等待处理，worker 从零启动需要时间。消息保留在队列里，我稍后再回来确认结果。

[继续。]

发送失败会重试，同一 ID 在接收端会去重。因此这是至少一次传输加去重存储，不能称为网络层的恰好一次传输。

## 7｜05:50–07:05｜Kubernetes YAML 与持久化

[依次展示已定位的 YAML 字段。]

前端 Deployment 指定 Docker Hub 镜像和副本数量，Service 将它暴露为 NodePort。任务服务配置了健康检查、就绪检查和资源预算，数据库连接凭据通过 Secret 引用传入。

数据库配置中的 instances 是三，storage 为每个实例申请持久卷。同步复制要求有一个 standby 确认，以提高已经提交数据的可靠性，但这也意味着备用节点不足时，写入可用性会受到影响。

这份 HPA 配置让不同业务 API 按各自 CPU 负载扩容。另一份 KEDA 配置根据未投递消息数量，将发送 worker 调整到零到四个副本。collector 保持运行，所以 worker 为零时仍然能够发现新任务。

当前部署固定使用一个 OrbStack 节点，三个数据库实例都可以在这台机器上运行。增加应用副本可以提高处理并发，但所有副本仍共享这台机器的资源。

## 9｜07:50–09:05｜收益、挑战、安全与验证边界

[显示架构图，再展示历史 HA/队列验证记录的日期和结果。]

这种设计可以分别部署和扩容不同组件，在设备流量较高时，不必把全部服务一起扩容。持久队列也能缓冲短暂故障。

代价是更多部署资源、数据库连接、日志排查和最终一致性问题。对于一个小家庭，这样的架构确实偏重。可以假设面对更大的设备群来解释扩容价值，但当前项目还没有实现多租户隔离。

安全方面，已经实现服务数据库账号隔离、受限权限、数据库 TLS 校验，以及内部信号端点的令牌保护。生产使用还需要用户认证授权、入口 HTTPS、网络策略和异地备份。JSON 编码本身并不提供加密。

这份历史测试记录显示，数据库主 Pod 故障后发生了自动切换，已提交任务得到保留，并且可以继续写入。但期间出现过 API 错误，恢复读取约用了三分钟，所以它证明的是故障恢复，不是无中断服务，也不能证明整台主机丢失后仍然可用。
